# 2026.327.1941 — feat: pull declared default models and gate the start on GPU readiness

## Summary

Two start-time changes to the `ollama` candy's service, plus a version catch-up.

**1. Declared default models (`OLLAMA_PULL_MODELS`).** The service runs a charly-owned wrapper,
`/opt/ollama/start-ollama.sh`, that starts `ollama serve` and rides an idempotent pull of the
declared model ids alongside it as a background child (bounded API wait, logs to the container
log). It forwards TERM/INT/QUIT, waits for the server to exit and returns the server's own exit
code, so supervisord supervises ONE process, a restart cannot race the old server for port
11434, and a failed pull never changes the server's supervisor state. The list is EMPTY here on
purpose: CPU-only consumers must not start downloading gigabytes; the list belongs one layer up.

**2. GPU-readiness gate (RCA-driven).** A live RCA (8 steps on #10) found this pod's server
CPU-only for 31 h while `nvidia-smi` inside the same container listed the card: `ollama serve`
discovers GPUs ONCE, at startup, by creating a CUDA context; under VRAM pressure that fails, the
device is skipped as `skipping pseudo-device with zero memory`, and the server stays CPU-only
for its lifetime. The wrapper waits for a GPU reporting ≥ `OLLAMA_GPU_MIN_FREE_MIB` (512) MiB
free, up to `OLLAMA_GPU_WAIT_SECONDS` (600), then exits non-zero and supervisord retries;
`OLLAMA_GPU_MIN_FREE_MIB=0` opts into CPU fallback deliberately. No `/dev/nvidiactl` ⇒ the gate
returns immediately, so the candy stays GPU-agnostic.

**3. Version catch-up.** `OLLAMA_VERSION` v0.40.16 → v0.40.17; `require:` `layer-supervisord`
v2026.271.1817 → v2026.314.0710.

## Missed controls (R1 — why the author's own gate did not catch these)

- **The TERM race (round 1).** The pre-push test asserted the wrapper's exit CODE but never
  WHEN the child exited: the fake server exited instantly, so the early-return path was never
  travelled. Missed control: the plan had no stop/restart test at all — a service wrapper whose
  stop path is untested was shipped on a pull-path test alone. Now the stop path is asserted
  with a slow-exiting server (exit code AND elapsed time).
- **The missing pull coverage (round 2).** No committed check was authored WITH the feature;
  body-only behavioural evidence was accepted as R7 coverage. Missed control: the R7 self-audit
  checked that the change was *described*, not that a check in the tree would fail without it.
- **The vacuous gate check (round 3).** The check's guard (`[ -e /dev/nvidiactl ] || exit 0`)
  meant its failing branch never executed on the CPU-only bed I first chose, so its PASS proved
  nothing. Missed control: I did not ask, per new check, "on THIS target, does the failing
  branch actually run?" Now the CPU path prints an explicit SKIP, and the GPU bed carries
  probes that cannot pass without the device and the refusal.

## Round-1/2 review fixes (carried)

- **TERM (R7/QUAL):** wait again for the child after a forwarded signal and propagate its real
  status — `WRAPPER_EXIT=7 elapsed_ms=2513`.
- **Committed coverage (R10/A2):** three runtime checks in the candy's plan —
  `ollama-wrapper-entrypoint` (bracketed `start[-]ollama` regex so the probe cannot match its own
  command line; measured exit 1 on an image without the wrapper, 0 with it),
  `ollama-pull-declared-model`, and `ollama-gpu-gate-refuses`.
- **Probe-bed build failure (R1):** RCA'd and filed as opencharly/charly#1252 (a one-off box
  queued ~30 min on an image lock, then could not resolve its derived `arch` base). The ad-hoc
  spike box was removed.
