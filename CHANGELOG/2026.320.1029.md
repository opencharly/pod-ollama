# 2026.320.1029 — chore(deps): bump OLLAMA_VERSION to v0.40.16 and give the pin coverage that fails

## Summary

`OLLAMA_VERSION` moves `v0.32.14` → `v0.40.16`, upstream's current release
(published 2026-11-09; `v0.40.17-rc0` is a pre-release). The var binds the TARBALL
install path only — on Arch and its derivatives the `ollama` package is installed
and pacman owns the version.

The bump alone would have shipped unproven, and that is the substantive half of this
change: **every step in the plan passed at ANY upstream release.** The runtime
`ollama --version` step asserted only the `^ollama version` PREFIX, and the API steps
asserted that something served, not which binary. So a bed over a version bump could
not have gone red — the coverage was vacuous for exactly this change class. Adds
`ollama-version-pinned`, a build-scope step asserting the installed binary reports
`0.40.16`. It carries `exclude_distro: [arch, cachyos]` because this pin does not
bind on the packaged path, where pacman's own lag would turn the step into a false
failure; the skip there is the design, not a missing assertion.

The prose is part of the change, so its numbers were re-measured instead of carried
forward, and two inherited claims turned out to be false and are not repeated.

Measured this round (commands in "How tested"):

- packaged base **66 → 75 MiB installed, 16 → 19 MiB download** (`ollama-0.40.16-2`);
- upstream tarball **1.32 → 1.44 GiB compressed** (`ollama-linux-amd64.tar.zst` at `v0.40.16`);
- `ollama-cuda` **~988 → ~496 MiB**, `ollama-rocm` **~2.9 GiB → ~1.0 GiB**.

Two claims that the bump's neighbourhood asserted and the artifacts refute:

1. The skill explained the ROCm size drop as "depends on `hipblas` instead of bundling
   ROCm". **Both 0.32.14 and 0.40.16 declare the same `depend = hipblas`**, so the
   drop is the package's CONTENT moving, not a dependency change. The skill now says
   to measure it per release and gives the command.
2. The ollama skill said `ollama-cuda`/`ollama-rocm` are "candies in this repository".
   They are not — this repo DEFINES one candy, `ollama`; those two live in
   `layer-ollama-cuda` / `layer-ollama-rocm`. (The `checked 3 candies` line in the gate
   output below is not a count of what this repo defines: `charly box list candies`
   names `ollama` plus the two candies this candy's `require: layer-supervisord` pulls
   in — `github.com/opencharly/layer-supervisord` and its `supervisord` entity.)

Also corrected: the Arch comment claimed `0.32.14-1` "landed the day upstream tagged
v0.32.14"; `0.40.16-2` was **built 2026-11-11**, two days after the 2026-11-09
announcement, so the comment now states the measured dates rather than a claim about
Arch's cadence.

run pasted above.

## Change classification

**Breaking change + rollback:** none — no API and no entity shape changes; this repo's
consumers pick up a newer upstream release the next time their images rebuild, and one
that must stay on `v0.32.14` pins a pod-ollama tag rather than following `main`.
Rollback is reverting this commit; the next build fetches the old tarball again (the
download cache is keyed by URL sha256, so the old key still serves the old archive).

Change class: **Candy config** — static gate `charly box validate`, live gate the
composing bed `check-ollama-pod` + its fresh-rebuild re-verification.

Two consumer legs follow producer-first, and neither is a deferral of work in THIS
repo's scope: (a) `distro-fedora`'s `box/ollama` still pins a released tag and advances
to this commit's tag in the next leg, which is where the pin actually reaches an image;
(b) the CachyOS boxes and the two backend layers carry the same stale pin — filed
below, because on CachyOS the version comes from the package, so that leg needs its own
GPU beds for a pin-only edit.
